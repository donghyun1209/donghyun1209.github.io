  사용자가 "포스트 만들어줘", "오늘 작업 포스트로 올려줘", "ToDayWork 기반으로 포스트 작성해줘",

  ToDayWork.md 내용을 분석해 제목·카테고리·태그를 추론하고, _posts/ 디렉토리에 Jekyll 포스트 파일을 작성한다.
---

## 목표

`ToDayWork.md`를 읽어 `_posts/YYYY-MM-DD-<slug>.md` 형식의 Jekyll 포스트 파일을 생성한다.

---

## 단계

### 1. ToDayWork.md 읽기

프로젝트 루트의 `ToDayWork.md`를 읽는다.
파일이 없으면 사용자에게 알리고 중단한다.

### 2. 메타데이터 추론

`ToDayWork.md` 내용을 분석해 다음을 결정한다.

**title**
- 파일 최상단 `#` 제목을 그대로 사용한다.
- 없으면 내용에서 핵심 주제를 뽑아 "프로젝트명: 핵심 작업" 형태로 만든다.

**date**
- 파일 내 날짜 표기(`> YYYY-MM-DD` 또는 날짜 언급)를 우선 사용한다.
- 없으면 오늘 날짜를 사용한다.
- 시간은 항상 `09:00:00 +0900`으로 고정한다.

**categories**
- 2개 이내로 결정한다.
- 프로젝트 이름(예: RasEyes, HelloWorld)과 기술 분야(예: Embedded System, Web, Algorithm)를 조합한다.

**tags**
- 본문에 등장하는 기술·도구·라이브러리·키워드를 소문자로 추출한다 (5~10개).

**slug**
- title에서 영문 소문자 + 숫자 + 하이픈만 남긴다.
- 예: "RasEyes Phase 4: Orange Pi 5" → `raseyes-phase4-orangepi5`

### 3. 포스트 본문 작성

기존 포스트 형식을 따르되, 말투는 항상 `_posts/2026-05-29-orangepi5-ubuntu-flashing.md`를 기준으로 삼는다. 이 포스트가 이 블로그의 "정답 톤"이다.

**말투 (가장 중요)**
- 문장은 "-다"로 끝나는 일기체로 쓴다 (했다/였다/뒀다/걸렸다). "~했습니다/~입니다" 같은 격식체 보고서 톤은 절대 쓰지 않는다.
- 1인칭 서술로, 그 작업을 하면서 실제로 느낀 답답함·의심·안도감이 드러나게 쓴다. "~를 구현했습니다", "~를 개선했습니다" 같은 산출물 나열형 문장은 피한다.
- 여러 개의 기술 항목을 그냥 나열하지 않는다. 각 항목도 "뭘 하려고 했는데 → 뭐가 안 됐는데 → 알고 보니 → 이렇게 해결했다"는 흐름으로 최대한 풀어 쓴다. 문제/실패가 없는 단순 작업이면 담담한 서술체로 쓰되, 스펙 나열 톤은 피한다.
- 코드 블록·표는 꼭 필요한 핵심 하나 정도로 최소화한다. 함수/파라미터를 줄줄이 나열하는 리스트보다 문장으로 풀어 설명하는 쪽을 우선한다.
- 소제목은 "1. 카메라 HAL 구현" 같은 스펙 문서 톤이 아니라, 그날 겪은 일을 요약하는 문장형으로 쓴다 (예: "ToF 센서가 다짜고짜 프로세스를 죽였다").

**형식 규칙**
- 한국어 문장과 영어 번역을 `\\`으로 구분해 같은 줄에 작성한다.
  ```
  한국어 설명.\\
  English explanation.
  ```
- 섹션 구분은 `---`를 사용한다.
- `ToDayWork.md`의 "다음에 할 것" 섹션은 그대로 옮기지 않는다. 대신 포스트 맨 끝에 "N. 요약 및 교훈" 소제목을 두고, 오늘 배운 것 한두 문장과 다음에 할 일을 자연스러운 문장으로 마무리한다.

**front matter 템플릿**
```yaml
---
title: "제목"
date: YYYY-MM-DD 09:00:00 +0900
categories: [카테고리1, 카테고리2]
tags: [태그1, 태그2, ...]
---
```

### 4. 추가 자료 필요 여부 확인

본문을 쓰다가 아래에 해당하는 부분을 만나면, 이미지 경로나 수치를 지어내지 말고 그 자리에 HTML 주석으로 표시만 남긴 뒤 넘어간다.

- 스크린샷/사진이 있으면 훨씬 이해가 쉬운 상황(에러 화면, 하드웨어 배치, 결과물 등)인데 `ToDayWork.md`에 이미지가 없는 경우
- `ToDayWork.md`에 이미지 경로(`![...](...)`)가 적혀 있지만 `images/` 디렉토리에 실제 파일이 없는 경우
- 벤치마크 표·그래프·수치가 언급만 되고 원본 로그나 캡처가 `ToDayWork.md`에 없어 표를 그대로 옮기기 애매한 경우
- 코드 스니펫이 필요한데 `ToDayWork.md`에 실제 코드가 없어 임의로 재구성해야 하는 경우

표시 형식 (렌더링되지 않는 HTML 주석이라 배포해도 화면에 보이지 않는다):
```
<!-- NEED: 오렌지파이5 배선 사진 -->
```

### 5. 파일 저장

`_posts/YYYY-MM-DD-<slug>.md` 경로로 저장한다.

저장 후 다음을 출력한다:
```
포스트 생성 완료: _posts/YYYY-MM-DD-<slug>.md
제목: ...
날짜: ...
카테고리: ...
태그: ...
```

본문에 `<!-- NEED: ... -->` 표시를 하나라도 남겼다면, 완료 메시지 뒤에 이어서 반드시 알려준다:
```
추가로 필요한 자료:
- (필요한 내용) — 위치: "## 관련 소제목"
- ...
```

표시가 하나도 없으면 이 항목은 출력하지 않는다.

---

## 주의사항

- 날짜 시간은 항상 `09:00:00 +0900`으로 설정한다 (미래 시간으로 설정하면 GitHub Pages 빌드 시 포스트가 숨겨진다).
- 같은 날짜의 포스트 파일이 이미 존재하면 덮어쓰기 전에 사용자에게 확인한다.
- `ToDayWork.md`의 내용을 그대로 복사하지 말고, 블로그 독자를 위한 흐름 있는 글로 재구성한다.
- 이미지 경로, 벤치마크 수치, 코드 스니펫 등 `ToDayWork.md`에 없는 자료는 절대 지어내지 않는다. 반드시 `<!-- NEED: ... -->` 표시로 남기고 사용자에게 알린다.
